# 온보딩 "환경설정 10분" 측정 프로토콜

> **문서 상태**: 프로토콜 정의(아래 전체)는 확정 초안이다. 실측 3회는
> 아직 수행하지 않았고(§9), §2의 구간 A/B 중 어느 쪽을 harness#97 목표
> 1의 공식 판정 근거로 쓸지는 미결정이다 — 이슈 오너가 결정한다.

harness#99 scope "10분 측정 프로토콜 정의 + 실측 3회" 중 프로토콜 정의
부분이다. 실측 3회는 이 문서로 진행하되, 참여자(harness를 처음 접하는
3인)가 필요해 별도로 진행한다.

## 0. 근거 문서

- 엄브렐러 harness#97 목표 1: "처음 접한 사용자가 에이전트 설치부터 harness
  진입까지 10분 안에 끝낸다", AC는 "harness를 처음 쓰는 참여자 3인이 10분
  안에 `/ait:welcome`까지 도달 — 측정 로그 3건 첨부".
- harness#99 scope: "10분 측정 프로토콜 정의 + 실측 3회 (엄브렐러 U 목표 1의
  판정 근거)", 소관 절: "에이전트 CLI 자체의 설치 난이도는 (v) 제품
  결정#100"으로 harness#99 자체 소관에서 제외.
- `README.md` "빠른 시작" 절(origin/main 기준, 아래 §1 복붙 블록과 대조
  확인).

### 시작점 정의에 남은 불일치 — 먼저 확정이 필요

harness#97 목표 1의 문구("에이전트 설치부터")와 harness#99의 소관 구분
("에이전트 CLI 자체의 설치 난이도는 ... #100")이 서로 다른 시작점을
가리킨다. 이 프로토콜은 그 불일치를 해소하지 않고 **두 구간을 모두 잴 수
있게 설계**했다(§2). 어느 쪽을 harness#97 AC의 공식 판정 근거로 쓸지는
이슈 오너가 결정할 문제로 남겨둔다.

## 1. 측정 대상 (요약)

README "빠른 시작" 절은 준비물 4가지(Node 24 이상, pnpm 11.17.0, git,
앱인토스 콘솔 계정)를 전제로, 아래 복붙 블록으로 harness 진입부터
`/ait:welcome`까지 안내한다(Claude Code 기준, 인용):

```
# 1) harness 플러그인 마켓플레이스 등록
/plugin marketplace add toss/apps-in-toss-harness

# 2) ait 플러그인 설치 (skill 8종 + MCP 서버 2개 자동 등록)
/plugin install ait@apps-in-toss

# 3) 콘솔 MCP 인가 (OAuth, 최초 1회) — 문서 MCP(apps-in-toss-docs)는 인증 없이 자동 연결됨
/mcp

# 4) harness 진입 지도 확인
/ait:welcome
```

Codex 참여자는 README "Codex에서 쓰기" 절의 동일 구조 블록
(`codex plugin marketplace add` → `codex plugin add` → `codex mcp login` →
`/ait:welcome`)을 쓴다.

## 2. 측정 구간 정의

두 구간을 구분해서 잰다. **구간 B가 harness#99의 실제 소관 범위와 일치하고,
이 프로토콜의 기본 측정값이다.** 구간 A는 harness#97 문구를 문자 그대로
따를 경우를 위한 참고값으로, 값을 얻을 수 있으면 함께 기록한다.

| 구간 | 시작(T0) | 종료(T1) | 비고 |
|---|---|---|---|
| **A. 전체(참고)** | 참여자가 에이전트 CLI(Claude Code 또는 Codex) 설치를 시작하는 시점 | `/ait:welcome`의 출력이 화면에 완전히 렌더링된 시점 | harness#97 목표 1 문구 그대로. 에이전트 CLI 설치 자체는 harness#99 소관 밖(#100)이므로, 이 구간의 병목이 에이전트 CLI 쪽이면 그 사실을 진단 결과로 분리해 기록한다. |
| **B. harness 진입(기본)** | 에이전트 CLI가 이미 설치·실행 가능한 상태에서, 참여자가 README 복붙 블록의 **1번째 줄**(`/plugin marketplace add toss/apps-in-toss-harness` 또는 `codex plugin marketplace add toss/apps-in-toss-harness`)을 실행(붙여넣기 + 엔터)한 시점 | `/ait:welcome`의 출력이 화면에 완전히 렌더링된 시점 | harness#99 소관과 정확히 일치. README 복붙 블록 자체가 측정 대상이므로, 이 구간의 값이 README 개선 여부를 직접 판정한다. |

두 구간 모두 종료점은 동일하게 `/ait:welcome` 출력 완료다 — harness#97
AC의 문구를 그대로 따른 것이며, `/ait:new` 등 이후 단계는 포함하지 않는다
(그 이후는 harness#97 목표 2, 50분 예산의 영역).

## 3. 참여자 조건

- **harness 최초 사용자**: 이 harness 플러그인·`ait` 명령을 이전에 써본
  적이 없는 사람. 팀 내부 도그푸딩이라도 재사용 참여자는 배제한다(캐시된
  경험이 시간을 왜곡한다).
- **환경 초기화 상태**: 측정 시작 시점에 `ait` 플러그인이 설치돼 있지 않은
  상태에서 시작한다. Claude Code는 `/plugin list`로 설치 여부를 확인하고,
  과거에 설치한 적이 있는 머신을 재사용하는 경우 `/plugin marketplace
  remove <marketplace-name>`·`/plugin uninstall <plugin>@<marketplace>`로
  제거한 뒤 시작했음을 기록 양식의 "환경 초기화" 컬럼에 남긴다(세 명령
  모두 공식 문서로 구문을 확인했다). Codex도 플러그인 관리 명령이 있으나,
  정확한 구문은 이 프로토콜 작성 시점에 공식 문서로 확인하지 못했다 —
  관찰자가 실측 착수 전 Codex CLI 도움말로 확인한 뒤, 설치돼 있지 않은
  상태에서 시작하거나 기존 설치를 제거하고 시작했다는 사실만 같은 컬럼에
  남긴다. 신규 계정·신규 머신이 가장 깨끗하지만 필수는 아니다.
- **사전 준비물은 미리 충족**: Node 24 이상, pnpm 11.17.0, git, 앱인토스
  콘솔 계정 — README가 "빠른 시작" 이전에 전제로 까는 4가지다. 이 준비물
  자체를 갖추는 시간(예: 콘솔 계정 신규 가입)은 구간 A·B 어디에도 포함하지
  않는다 — README 문구상 이들은 복붙 블록의 전제이지 블록의 일부가 아니다.
  참여자가 이 중 하나라도 사전에 갖추지 못한 상태라면 그 사실을 기록하고
  측정을 시작하지 않는다(별도 트랙: "준비물 자체가 장벽"인지는 진단 메모로
  남기되 10분 타이머에는 넣지 않는다).
- **에이전트(Claude Code / Codex) 선택**: 참여자당 1개 에이전트로 측정한다.
  3인 중 최소 1인은 Codex로 측정하는 것을 권장한다 — Codex 절은 별도
  블록이라 Claude Code 절만으로는 판정 근거가 되지 않는다.
- **사전 지식**: harness·앱인토스 미니앱 개발 경험이 없는 참여자를 우선한다
  (도그푸딩 취지상 "처음 접한 사용자"). 완전히 배제가 어려우면 참여자의
  사전 경험 수준(예: "앱인토스 SDK 경험 있음/없음", "Claude Code 사용
  경험 있음/없음")을 기록 양식에 남겨 해석 시 참고한다.
- **관찰자 동석**: 측정마다 관찰자(측정자) 1인이 동석하거나 화면 녹화로
  대체한다(§4).

## 4. 측정 방법 — 무엇을 타임스탬프로 남기는가

- 관찰자가 참여자 화면을 보면서(대면 동석 또는 화면 공유/녹화) 아래
  이벤트마다 벽시계 시각(초 단위)을 기록한다.
  1. T0 — 복붙 블록 1번째 줄 실행 시점(구간 B 시작)
  2. `marketplace add` 완료 시점(콘솔/채팅창에 완료 메시지 표시)
  3. `plugin install` 완료 시점
  4. `/mcp` 콘솔 OAuth 인가 완료 시점(브라우저 인가 화면 통과 포함)
  5. T1 — `/ait:welcome` 출력이 화면에 완전히 표시된 시점(구간 B 종료)
  - 구간 A를 함께 잴 경우, 에이전트 CLI 설치 시작 시점도 T0-A로 별도 기록.
- **화면 녹화를 권장**한다 — 어느 단계에서 얼마나 멈췄는지 사후 확인이
  가능하고, 실패 시 원인 진단에도 쓴다. 녹화본에 자격증명(콘솔 로그인
  정보·OAuth 토큰)·사내 식별자(dog-food 워크스페이스 번호 등)가 노출되지
  않는지 녹화 종료 직후 확인한다 — 노출됐다면 그 구간을 잘라내거나
  녹화본을 폐기한다.
- 타임스탬프는 관찰자의 스톱워치/화면녹화 타임코드 중 하나로 통일한다 —
  참여자 발화("지금 시작했어요")에 의존하지 않는다.

## 5. 중단·실패 처리

- **원칙**: 참여자가 막히면 먼저 스스로 해결을 시도하게 둔다. 관찰자는
  진행을 유도하는 힌트를 주지 않는다 — 이 측정의 목적이 "안내 없이 문서만
  보고 도달 가능한가"이기 때문이다. 예외는 보안·안전 문제(예: 자격증명을
  잘못된 곳에 붙여넣으려는 경우)뿐이며, 그 경우 즉시 개입한다.
- **시간 상한**: 목표(10분)에 여유를 더해 **T0로부터 15분**까지 자력
  해결을 허용한다. 15분을 넘기면 그 시점에 "실패"로 기록하고 타이머를
  멈춘다. 그 이후 관찰자가 개입해 막힌 지점의 원인을 진단하되, 그 개입
  이후 걸린 시간은 측정값에 포함하지 않는다(진단 메모로만 남긴다).
- **조기 종료**: 참여자가 중도 포기 의사를 밝히면 15분을 채우지 않아도
  즉시 "실패"로 기록하고 종료한다.
- **막힌 지점 기록은 필수**: 실패든 시간 내 성공이든, 각 단계 사이에 1분
  이상 멈춘 구간이 있으면 그 지점과 사유(에러 메시지 원문 또는 화면
  스크린샷 — 자격증명·사내 식별자는 가리고 보존)를 남긴다. 이 기록이
  README·프로토콜 개선의 직접 입력이 된다.

## 7. 결과 해석 기준 (제안)

harness#97 AC 원문은 "참여자 3인이 10분 안에 `/ait:welcome`까지 도달"이다
— 문면상으로는 3/3 전원 성공을 요구하는 것으로 읽힌다. 이 문서는 그
원문을 기본 판정 기준으로 제안하되, 실측이 애매하게 나올 경우를 대비해
등급을 나눠 보고할 것을 권한다.

- **목표 달성(제안)**: 구간 B 기준 3/3이 10분 이내 성공.
- **부분 달성**: 구간 B 기준 2/3이 10분 이내 성공, 1건은 10~15분 또는
  실패. 이 경우 목표 자체는 미달성으로 보고하되, 실패/지연 1건의 막힌
  단계를 README 개선 항목으로 바로 연결한다.
- **미달성**: 1/3 이하 성공.
- 위 등급 구분과 "3/3 요구"의 엄격도는 harness#97 이슈 오너(소관 (v) 제품
  결정)가 최종 판정한다 — 이 프로토콜은 판정 절차를 제안할 뿐 기준을
  확정하지 않는다.
- 구간 A(전체, 에이전트 CLI 설치 포함) 값을 함께 얻었다면, 구간 B는
  목표 내인데 구간 A가 초과하는 경우가 나올 수 있다 — 그 경우 병목이
  harness#99 소관이 아니라 에이전트 CLI 설치(harness#100/제품 결정)
  쪽에 있다는 근거로 분리해서 보고한다.

## 8. 보안·프라이버시 유의사항

- 녹화본·스크린샷·기록 양식 어디에도 Deploy Key·TOTP 등 자격증명, dog-food
  워크스페이스 번호·miniAppId, 참여자의 로컬 절대경로(사용자명 노출),
  사내 도메인·서비스명을 남기지 않는다 — `docs/bug-report-guide.md`의
  "시작하기 전에 — 시크릿·사내 식별자" 절과 동일한 기준을 적용한다.
- 참여자 실명 대신 익명 ID를 쓴다.

## 9. 확인하지 못한 것 (정직 고지)

- 실측 3회는 미수행이다(참여자 필요, scope 지시에 따라 이 세션에서
  제외).
