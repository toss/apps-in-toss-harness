## 1. GW 결함 4건

### 결함 1 — `tools/list` description 전부 빈 문자열

- **현상**: `tools/list` 응답의 97종 tool 전부 `description` 필드가 빈 문자열.
- **재현 조건**: OAuth 인가 완료 후 `tools/list` 호출. 파라미터·워크스페이스 무관하게
  재현.
- **영향**: 에이전트가 tool 이름(예: `miniapp_create`, `bundle_upload`)만으로 용도·
  파라미터 의미·부작용 여부를 추론해야 한다. 스키마 발견 비용이 커지고, 특히 조회형과
  변이형(예: 검수 제출·릴리즈)을 이름만으로 구분해야 하는 상황에서 오호출 위험이
  높아진다.
- **요청**: 각 tool에 최소한 (a) 한 줄 용도 설명, (b) 파라미터 의미, (c) 부작용
  여부(read-only인지 상태를 바꾸는지)를 채워 달라.

### 결함 2 — `miniapp_category_list` 일관 실패

- **현상**: `MCP error -32000: 존재하지 않는 정보 입니다`.
- **재현 조건**: 파라미터 무관하게 매 호출 재현, 3~4회 재시도해도 동일한 에러.
- **영향**: 카테고리 조회가 불가능해 신규 앱 등록 시 category 설정 단계에서 대체
  수단 없이 막힌다.
- **요청**: 서버측 원인을 확인해 수정하거나, 수정이 당장 어렵다면 최소한 에러
  메시지를 실제 원인이 드러나도록 구체화해 달라(`-32000` + 고정 문구는 원인 추정이
  불가능하다).

### 결함 3 — `image_upload_url` 일관 실패

- **현상**: 결함 2와 동일한 `-32000` 에러.
- **재현 조건**: 파라미터 무관하게 일관 실패.
- **영향**: 신규 앱 아이콘 업로드가 구조적으로 불가능하다. harness 쪽 E2E 완주
  실증에서는 신규 아이콘 업로드 대신 기존 공개 아이콘 URL을 재사용하는 우회로
  넘어갔지만, 이는 임시 우회일 뿐 정상 경로가 아니다.
- **요청**: 수정 필요 — 대체 수단이 없으면 신규 앱은 아이콘을 올릴 방법이 아예
  없다.

### 결함 4 — `bundle_build_status` 일관 실패

- **현상**: 결함 2·3과 동일한 `-32000` 에러.
- **재현 조건**: 파라미터 무관하게 일관 실패.
- **영향**: 배포 E2E에서 컴파일 상태 폴링을 이 tool로 할 수 없다. 현재는
  `miniapp_get_status`·`bundle_list`로 상태를 우회 확인하고 있다.
- **요청**: 수정되면 컴파일 상태 폴링 경로를 이 tool 기반으로 재작성할 예정이다
  (harness#43 본문에 후속 이슈로 이미 예고돼 있다).

## 2. Deploy Key 발급 tool 부재 — headless CI 발급 경로 요구사항

- **현상**: GW tool 인벤토리 97종(workspace 6 / miniapp 14 / bundle 9 / review 5 /
  push 12 / iap 8 / iaa 14 / promotion 11 / dashboard 8 / event 5 / notice 2 /
  toss_login 2 / image_upload_url 1) 전수 확인 결과 `keys_*` 계열 tool이 존재하지
  않는다.
- **영향**: 워크스페이스-scope 자격증명(Deploy Key) 발급·조회가 여전히 콘솔 UI 또는
  구 CLI(aitcc) 의존이다. GW OAuth는 계정-scope·대화형 인가 모델이라 이 gap을
  메우지 못한다 — headless(CI/CD) 환경에서는 애초에 대화형 OAuth 흐름을 탈 수
  없기 때문에, GW 인증만으로는 CI 파이프라인에서 콘솔 자동화를 완결할 수 없다.
- **headless CI 발급 경로에 필요한 최소 요구사항**:
  1. Deploy Key를 발급/조회/폐기할 수 있는 tool(예: `keys_create`, `keys_list`,
     `keys_revoke`) 추가.
  2. 위 tool 호출 자체는 계정-scope 대화형 인가(기존 OAuth)로 수행하되, 발급된
     Deploy Key는 워크스페이스-scope로 별도 저장·전달되어 이후 CI에서는 그 키만으로
     인증할 수 있어야 한다(즉 Deploy Key 발급은 대화형, Deploy Key *사용*은
     headless).
  3. 발급 응답에 키 값이 노출되는 것은 불가피하지만, 시크릿이 로그·에러 메시지에
     반복 노출되지 않도록 처리(1회성 표시 등) 검토.
- **요청**: Deploy Key 발급/조회용 tool 추가를 검토해 달라.

## 3. 공통 사항

- 시크릿·토큰 값은 이 문서를 포함해 어떤 파일·로그·커밋에도 기록하지 않는다
  (harness#43 본문 명시 원칙).
- 결함 재현에 사용한 실제 워크스페이스는 "테스트 워크스페이스"로만 지칭한다 —
  구체 워크스페이스 번호·miniAppId는 사내 운영 기록에만 있고 이 문서에는 신지
  않는다.

## 4. 2차 관측 6건 (2026-08-07 도그푸딩)

1차 결함 4건 + `keys_*` tool 부재(§1~§2)에 이어, 같은 콘솔 MCP GW 사용 중
2026-08-07 도그푸딩 세션에서 추가로 관측된 결함·요구 6건. 시크릿·워크스페이스
번호·miniAppId는 포함하지 않는다.

1. **`shareLink`가 `intoss-private` 스킴을 지원하지 않음** — 진입 불가 또는
   이미 배포된 앱으로 오접근하는 결과가 나온다.
2. **콘솔 MCP가 private 스킴을 안내하지 않음** — 사용자가 어떤 스킴으로
   진입해야 하는지 알 방법이 없다.
3. **승인 전 input validation이 반복 차단**되고, AI 검수 결과 대기까지 겹쳐
   피드백 루프가 지연됨.
4. **워크스페이스가 두 개로 보이는 혼란** — 원인 미상, 사용자 관점에서 어느
   워크스페이스가 유효한지 판단 불가.
5. **미배포 앱도 "내 미니앱 목록"에 노출해 달라는 요구.**
6. **번들 업로드 응답에 `intoss-private` 진입 링크 파라미터를 포함해 달라는
   요구** — 해소되면 harness#98(실기기 테스트 정규 경로)의 "진입 스킴/링크
   손조립 금지 가드" 항목이 원천적으로 불필요해진다.

- **재현 조건**: 1차와 동일한 dog-food 재사용 타겟, 같은 console MCP GW 세션.
- **요청**: 1차 5건과 함께 같은 전달 채널로 묶어 GW 운영팀에 전달한다(별도
  전달 트리거를 새로 만들지 않는다).
